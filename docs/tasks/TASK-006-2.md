>

## 실행 경과 및 이슈 처리 (교훈)

1. **dry-run만으로는 "계좌명+계좌번호 조합 매칭 리스크"를 완전히 검증하지 못했다.** 대조표를 만들 때 시트 계좌명(줄바꿈 앞부분)만 비교했는데, 실제로는 기존 시드 데이터 중 2개 계좌가 계좌명에 세부식별자까지 통짜로 포함되어 있어(`처리투자(미래에셋)`) `account_name` 자체가 다른 값이었다. dry-run 단계에서 "DB의 `account_name` 컬럼 원본 값"과 "파서가 실제로 만들어낼 `account_name` 값"을 직접 SQL로 대조했다면 사전에 발견할 수 있었다.
2. **실제 반영 직후 결과가 예상과 다르면 즉시 원인 파악 → 최소 범위로 되돌리기 → 재검증 → 재실행 순서로 대응했다.** 여기서는 잘못 생성된 계좌 2개와 그 스냅샷만 정확히 골라 삭제했고, 다른 6개 계좌의 정상 데이터는 건드리지 않았다.
3. **표시 단계(UI)에서 발견된 이중 괄호 문제도 데이터 근본 원인(계좌번호 필드에 괄호 포함)까지 추적해 수정했다.** 단순히 컴포넌트에서 문자열을 잘라내는 임시방편 대신, 파서와 DB 양쪽에서 데이터 자체를 정규화했다.

## 주의사항

1. **`.env.local`의 `CRON_SECRET`은 로컬 개발용 임시값**: Task 008(배포) 시 프로덕션용으로 교체 필요
2. **any 타입 금지**: 전역 규칙 준수, 최종 코드에서도 위반 없음
3. **Vercel Cron 실등록은 여전히 범위 밖**: Task 008(배포)에서 진행
4. **`은퇴 투자(삼성증권)` 계좌는 시트에 실제 데이터가 있지만 의도적으로 수집 제외 상태**: `parser.ts`의 `EXCLUDED_ACCOUNTS` 상수에 명시되어 있다. 향후 이 계좌도 수집하려면 해당 상수에서 제거하면 된다.
5. **다음 실행부터는 매일 최신 시세로 upsert된다**: `/api/cron/collect`를 재호출하면 `snapshot_date`(오늘)가 같으므로 새 값으로 갱신되고 중복 행이 생기지 않는다. 단, 아직 Vercel Cron이 등록되지 않아 자동 실행은 되지 않는다(Task 008에서 등록 예정) — 그 전까지는 로컬에서 수동 호출해야 한다.
